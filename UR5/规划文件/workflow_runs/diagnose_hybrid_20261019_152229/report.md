## 结论

不是RealHome缺失、版本错误、整圈跳变或焊接构型链失效。本次在`VELOCITY_OPTIMIZATION`中，C速度方案通过焊缝段验收后进入Hybrid-D。6次D尝试全部`quadprog exitflag=0`，每次达到1000次迭代上限，没有一次返回“证明不可行”的状态。程序将这些退出统称`QP_INFEASIBLE`，而调用端又要求必须生成新D，导致整次连续规划终止。

首轮D的原始矩阵有282个变量、35,880条不等式（11,592条TCP分量约束）。独立LP可行性检查exitflag=1，证明该组原约束存在可行解；不能把本次超时泛称为“约束无解”。但是同一QP改用LP可行初值后仍在1000次迭代处退出，说明初值不可行并非唯一问题。进一步优化应针对active-set收敛/冗余约束及失败回退处理，不能只提高限值或声称换初值即已修复。

整条任务尚未进入merge/global continuity/final controller validation，不能把焊缝C方案PASS等同于完整任务PASS，`executionReady=false`应继续保持。

## 3. 精确失败分支

- `UR5/matlab仿真/prepare_hmi_continuous_request.m:89`按`c.complete`分支。
- C已PASS，故第100行调用Hybrid；第101行把`hybridCandidateFound=false`直接升级为`PREPARE:Hybrid / Hybrid velocity generation failed`。
- `UR5/matlab仿真/optimize_accp_hybrid_velocity.m:148`使用active-set，`MaxIterations=1000`。
- 第153行把所有`flag<=0`统一丢弃；第40～42行统称`QP_INFEASIBLE`，未区分迭代耗尽/真正无解/数值错误。
- 该函数第62～63行实际已经将未找到D时的输出保留为通过验收的C，但调用端第101行不允许使用这个回退，存在返回契约与日常入口的不一致。

原失败报告没有保存Hybrid的attempts；本轮用其`velocity_profile_input_diagnostic.mat`及绑定scene/profile，重放**未修改的生产函数**，保存[完整退出详情](hybrid_replay.json)，耗时58.965924s：

## 4. 矩阵可行性与初值对照

诊断副本`hybrid_qp_readonly_probe.m`机械复用生产`localSolve`的矩阵组装，仅增加LP/初值对照，不修改生产函数或任何阈值，也不导出关节速度候选。

- D内部将每个TCP误差分量限制到`0.49/sqrt(3)=0.282901632`，比最终0.5mm/0.5°向量范数验收更保守。因此C虽然通过原门，不一定是D内部可行种子。
- C种子运动学不等式违反量为0；TCP分量框最大违反量0.115399859（各行按自身mm/deg单位）。这不等于C违反0.5mm验收。
- 全部原约束LP exitflag=1；仅运动学约束LP也为1。
- Hessian reciprocal condition约0.006707；没有证据把此次失败归因为Hessian奇异。
- 同一原QP、同样active-set和1000预算，仅用LP可行初值做独立对照，仍exitflag0/1000次（求解1.902621s）。没有确认得到可接受D，更没有整任务PASS。

见[矩阵可行性](qp_matrix_probe.json)、[可行初值对照](qp_initialization_comparison.json)。LP只用于证明矩阵可行性，不是放宽约束或生成可执行路径。不能把这项诊断结果直接写回正式轨迹。

## 5. 为什么旧任务成功而这次失败

上次12:14任务在旧限值下，C的同步0.566948mm、姿态0.549689°未通过，所以走第92行独立controller-aware速度恢复，之后完成全任务验证。

这次的新限值被正确读取（πrad/s、40rad/s²配置上界），使C速度生成进入不同可行区域；时间方案也变成23.348725s而非25.844522s。C同步0.428675mm、姿态0.280062°通过，于是进入此前被绕开的Hybrid-D分支，暴露其收敛/强制D成功的问题。

这是“阈值/时间输入改变后触发的分支缺陷”，不能归咎于用户把Home保存错。也不能把旧已优化轨迹的2倍缩时测试，当成新Home完整连续规划冷启动已经验证成功。
